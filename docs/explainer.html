whatsmyip

A tiny web app that returns your IP, shipped through a full CI pipeline into a local Kubernetes cluster.

Start here: one command deploys everything. 
make all
Measured: 41 s with warm caches. The first run on a new machine takes longer: it downloads the base images, k3s and the ~60 MB Trivy DB.

1. Run it

  1. Check the tools are installed. ~10 s 
    for t in docker k3d terraform helm uv trivy; do command -v $t >/dev/null || echo "missing: $t"; done
    No output = all present. Docker must be running.
  2. Deploy everything. ~1 min (warm caches) 
    make all
    Runs, in order: venv lint test build scan cluster-create deploy smoke. Last line: smoke ok.
  3. Call the app. ~5 s 
    curl -H 'X-Forwarded-For: 198.51.100.4' localhost:8080/
    Returns {"ip":"198.51.100.4"}.
  4. Tear it down when done. ~10 s 
    make cluster-delete
    Removes the cluster, the Terraform state and the cluster kubeconfig.

2. What works after make all

The app runs in Kubernetes on http://localhost:8080, 2 pods, namespace staging.
TryYou get
curl localhost:8080/health{"status":"ok"}
curl localhost:8080/ready{"status":"ready"}
KUBECONFIG=~/.kube/big-id-k3d-config.yaml kubectl -n staging get pods2 pods Running

The cluster has its own kubeconfig at ~/.kube/big-id-k3d-config.yaml. Your default kubeconfig is never touched.

Browser on localhost:8080 shows 10.42.x.x, not my IP. Expected.

See it yourself: make trace-hops captures one request at every hop and prints each source address.

10.42.0.1 (or 10.42.1.1, 10.42.x.0) is a node's address, not a pod and not you. Each local hop replaces the source address:

  1. Browser connects to 127.0.0.1:8080.
  2. Docker Desktop forwards the port into its VM: source becomes the VM's gateway.
  3. k3d load balancer (nginx, plain TCP proxy) opens a new connection: source becomes its container IP.
  4. ServiceLB and kube-proxy (externalTrafficPolicy: Cluster) apply SNAT: source becomes the node gateway.

Best case locally would be 127.0.0.1 or Docker's gateway. Browser and server run on the same machine, so there is no public client IP to see.

The app is correct. In production an internet-facing load balancer or ingress sets X-Forwarded-For, and the app returns the left-most entry. make smoke tests that path by sending the header. Details: README → Limitations.

3. Request path

client→localhost:8080→k3d load balancer→Service (LoadBalancer, ServiceLB)→2 pods: gunicorn :8080
  • App: Flask + gunicorn, distroless image, non-root, read-only filesystem, no shell.
  • Answer: the left-most X-Forwarded-For entry, else the connection's peer address.
  • Deploy: Terraform (infra/) creates the staging namespace and a Helm release of charts/whatsmyip. A failed rollout rolls back on its own.
  • Cluster: created by the k3d CLI (make cluster-create), not by Terraform. Traefik is off, so forwarded headers reach the app unchanged.

4. CI pipeline

Every push to main, every PR, or a manual run. Each job calls the same make targets as your laptop.

lint→test→build→scan→push→helm-lint→deploy + smoke→notify
JobDoesTook (first green run)
lintruff check + format check10 s
testpytest; a failing test fails the run9 s
buildDocker image tagged with the commit SHA32 s
scanTrivy blocks fixable HIGH/CRITICAL CVEs, uploads SARIF, saves the SBOM47 s
pushImage to GHCR (only if the scan passed)39 s
helm-linthelm lint --strict17 s
deployk3d cluster on the runner, terraform apply, then make smoke75 s
notifyCommit status ci/pipeline + job summary, always runs5 s

Total: about 4 minutes. On a PR, the image tag is the PR's head commit, never GitHub's merge commit.

Planned, built last: an AI step that runs only when the pipeline fails. It sends the failed logs to the Anthropic API and posts a diagnosis on the PR.

6. Stuck?

make all fails at build or cluster-create

Cause: Docker is not running. Fix: start Docker Desktop, then run make all again.

cluster-create fails: port 8080 in use

Cause: another process listens on 8080. Fix: lsof -i :8080, stop that process, then make cluster-delete all.

smoke: /ready failed

Cause: pods are not ready. Check: KUBECONFIG=~/.kube/big-id-k3d-config.yaml kubectl -n staging get pods, then kubectl describe pod on the failing one.

scan fails

Cause: Trivy found a fixable HIGH or CRITICAL CVE. Fix: bump the base image digest in Dockerfile or the pinned dependency in app/requirements.txt.
